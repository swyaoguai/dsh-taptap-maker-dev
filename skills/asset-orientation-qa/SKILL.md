# 资产朝向审查（Oriented Review）

## 这个技能解决什么

模型「朝哪边」这件事，**机器算不出来**。

一个建模时朝 +Z 的角色，和同一个角色朝 −Z，导出的 glTF 在字节层面可以完全
一致：同样的包围盒、同样的节点树、同样的动画片段。加载文件无法区分它们。
**只有看才能区分** —— 所以这必须是一个依赖视觉判断的检查步骤，而不是一条
启发式规则。

症状在成品游戏里一旦知道就极其明显，不知道时完全隐形：

- 角色明明在跑，看起来却是在横着平移；
- 敌人朝你冲锋，方向却是背对着你；
- 赛车用「车头朝后」的姿态在开；
- 宝箱是朝远离玩家的方向打开的。

**没有任何报错，没有任何测试失败，游戏就是错的。**

> 出处：本文的方法论核心（含"边界框完全相同"与各题材朝向判据）整合自
> OpenDCAI 的 3AGameFactory 项目 `agent_skills/asset_qa/3d_object/orientation_review.md`
> （Apache-2.0）。已改写为 TapTap Maker 语境。详见仓库根目录 `THIRD-PARTY-NOTICES.md`。

## 什么时候必须跑

- 任何 3D 模型导入 `assets/` 之后，**在宣称"这个游戏做完了"之前**；
- 当模型来源是外部资产包、AI 生成、或从别的引擎/项目搬来的；
- 只要有人反馈"角色朝错方向""走路像滑步""面朝别处"——先查这项；
- 反向的情况：**纯贴图、材质、音频、动画片段没有"正面"**，跳过本检查。

## 核心前提：先建立锚点

审查前必须先知道**本项目的"前方"是哪个轴**。别猜：

1. 查 `skills/taptap-maker-core` 与 `skills/taptap-maker-animation-fsm` 里关于
   Node 变换与 Root Motion 的实测结论；
2. 用一帧已知朝向的角色（或一个带明确正面的道具）做参照物落地验证一次；
3. 把结论写进项目文档（例如 `GAME_RULES.md` 的"坐标约定"一节），
   **后续所有资产都对照这一条**。

**没有这个锚点就去判断朝向，等于在猜。** 猜错比不记更糟——因为一条错误的
记录会让后来的人不再复查。

## 工作流

### 1. 渲染多个视角

对每个待审查的模型，至少拿到以下视角的**可辨认渲染图**（正交最佳）：

- 四个水平方向（+X / −X / +Z / −Z 各站一个相机看向原点）
- 一个俯视（+Y）

标注方式很关键：**标"相机在哪个轴上看"，不要标"这是正面"**——
标成"正面"就等于预先假定了答案，会诱导自己看错。

命名示例：`camera on +Z | screen right = +X`。

### 2. 找"脸"，按题材判据表

判断哪个视角里主体**正对着相机**。按可信度从高到低用这些线索：

| 题材 | 朝向的那一面会显示 |
|---|---|
| 人形 | 眼睛、鼻子、嘴、胸口、腰带扣、鞋尖 |
| 四足 | 口鼻与耳朵（尾巴在相反侧） |
| 载具 | 引擎盖、格栅、大灯、挡风玻璃的倾斜方向 |
| 枪械 | **枪口**（沿枪管方向 —— 这是唯一"前方不是脸"的题材） |
| 建筑 / 拱门 / 门洞 | 玩家会走进去的那个开口 |
| 箱子 / 柜子 / 冰箱 | 铰链在后、拉手/锁扣在前 |
| 飞行器 / 导弹 | 弹头/机头在前，喷口在后 |

**模型的 forward 轴 = 那个视角标注的轴。**

### 3. 用第二个视角交叉验证

单视角可能看错。用相邻视角做一致性检查：

> 例：若模型朝 +Z，那么在 `−X` 视角里（screen right = +Z）它的脸应当在
> 画面**右侧**；在 `+X` 视角里应当在**左侧**。对不上就是第 2 步读错了。

这一步能挡掉绝大多数误判，**别跳过**。

### 4. 检查"躺倒"

看俯视（+Y）图：站立的角色应该是一个**紧凑的小轮廓**（头顶/肩部）。
如果俯视图里出现了完整的人形（能看出手脚），说明模型是**躺着**的 ——
它是按 Z-up 建模的。

此时先记一个 pitch 修正（±90°，哪边能立起来用哪边），
**再**判断 yaw —— 因为躺倒会改变哪个轴才是水平方向。

### 5. 检查尺度

用场景里的参照物（门高、角色身高）对比模型的包围盒尺寸。

常见坑：一个"4.46 单位高"的角色不是 4.46 米高，而是一个 1.8 米的人用
不同单位建的。**按实际用途反推真实尺寸**，别直接信文件里的数字。

TapTap Maker 里还要注意：`skills/taptap-maker-camera` 记录了正交相机的
`orthoSize` 有 0.5 因子，尺度判断错会连带把画面构图搞错。

### 6. 记录，而不是改代码

**这是本技能最重要的一条规则。**

判定完成后，把结论写进**资产自己的元数据**（`.meta` 旁边的项目约定文件、
或项目内的 `assets-manifest.json` 之类），而不是在 gameplay 里补偿：

```
✅ 正确：在资产元数据里记 forward_axis = "+Z"，运行时统一应用
❌ 错误：在角色实体的 update 里写 node.rotation = Quaternion(0, PI, 0)
```

为什么错：游戏代码里的 `rotation += PI` 对**这个资产的其他所有消费者都是隐形的** ——
世界的摆放规则不知道、下一处引用它的地方不知道、按某个朝向做的动画也不知道；
而且一旦那个实体自己重新设置朝向，这个补偿就被**静默抹掉**。

一处记录，处处生效。

### 7. 复验

改完后再渲染一次，确认转过来的方向符合预期。**不要假设设置生效了** ——
朝向这类问题"看起来改好了但其实没生效"非常常见。

## 图像本身看不清时怎么办

**明确说看不清，而不是猜一个记录下来。**

一条错误的记录比没有记录更糟：它会让下一次检查直接跳过。

- **对称道具没有正面**（木箱、桶、石头）：明确写"无朝向"，说明原因。
- **贴图解码失败**：改用轮廓判断（鞋尖、鼻子、背包、尾巴、头发）。
- **斜 45° 朝向**：没有哪个主轴贴合。记录相对最近轴的**角度偏移**，
  并注明这是估算值。
- **五个视角都难以辨认**：建议**重新生成这个资产**，而不是硬标注。
  五个角度都看不出来的模型，进了游戏只会更糟。

## 明确不要做的事

- ❌ **不要在 gameplay 代码里旋转模型来"修"朝向**（同上，且会被静默覆盖）。
- ❌ **不要为了让画面看起来对而重新导出/重新生成模型** —— 那是在用几分钟
  GPU 时间去改一个字符串就能承载的事实。
- ❌ **不要手改运行时自动生成的 manifest** —— 它会在下次导入时被重写。
- ❌ **不要根据动画片段名字推断朝向** —— 一个叫 `Walking` 的片段朝哪个轴
  平移，取决于作者当时的选择，那是同一个未知量。
- ❌ **不要在没真正看图的情况下就打上"已经人工确认"的标记** ——
  那个标记是"有没有人查过"的唯一记录，伪造它等于毁掉整个机制。
