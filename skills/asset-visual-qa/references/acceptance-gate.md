# 验收门槛：什么时候可以说"做完了"

> 整合自 OpenDCAI 3AGameFactory 的 `agent_skills/setting_overview.md`
> 的「End-to-end workflow / Validate, play, and iterate / Completion rules」
> 三节（Apache-2.0），改写并适配 TapTap Maker 语境。
> 详见仓库根目录 `THIRD-PARTY-NOTICES.md`。

## 为什么需要这份文档

最常见的失败不是"做不出来"，而是**过早宣布做完了**。

agent 很容易因为「文件写完了」「编译过了」「启动没报错」就交付，
而用户打开一看：角色朝后跑、武器插在胸口、点开始没反应。

所以把「什么叫完成」写死，避免自欺。

---

## 一、先有白盒，再有美术

**顺序不能反。**

| 阶段 | 用什么 | 目标 | 允许的借口 |
|---|---|---|---|
| 白盒 | 简单几何体、纯色、占位音效 | 打通完整玩家循环 | 「美术还没上」可以接受 |
| 深化 | 正式资产 | 替换占位、保持接口不变 | 「美术没验收」**不可接受** |

白盒阶段的产物**必须登记为待替换**，不能算成品资产。

白盒要验证的是：场景能不能连起来、玩法能不能成立、UI 能不能操作、
章节切换顺不顺。这几件事通了，再谈美术。

**白盒通过不代表成品通过。** 换完资产必须重新跑一遍最终验收。

---

## 二、验证的定义（严格的）

以下**都不算**验证完成：

- ❌ 代码写完了
- ❌ 编译/构建通过
- ❌ 游戏能启动
- ❌ 日志里没有报错
- ❌ 看过一张截图

**算验证**的是：

1. **真的构建、启动、并且玩**
   - 跑**大部分**预定的玩家操作，不只是启动：
     移动 / 跳跃 / 冲刺 / 镜头 / 攻击或射击 / 交互或拾取 / 驾驶 /
     受伤与死亡 / 重生 / 胜利与失败 / 暂停 / 每个承诺过的界面
   - 核心循环至少完整跑通一次，外加设计里点名的边界情况
2. **录一段证据视频**（小分辨率、短视频，是证据不是预告片）
   - 覆盖：待机、移动、转向、主动作、载具（若有）、一次特效触发、
     一次完整 UI 操作、一次场景切换
3. **回看录像**
   - 逐条对照 `skills/asset-visual-qa` 的复核维度表
   - **绝不**通过源码或单张截图判断游戏好坏
4. **记录并修复**
   - 每条问题写清：现象 → 归属层 → 修法 → 新录像复验
5. **循环直到通过**
   - 重复 build → play → record → review，直到验收标准和维度表全过

## 三、完成规则（Completion rules）

- **保住原始验收标准**，不要因为另一个方案更好做就换成别的游戏或别的玩法。
- **资产、玩法、UI、引擎集成分成独立交付物**，各自通过各自的验证后才合并。
- **绝不仅因为"代码写完了"就说游戏能玩。** 构建、启动、代表性操作检查、
  视觉回看 —— 是四份互相独立的证据。
- 交付游戏时，必须完成上面的验收闭环，并**保留或汇报**最终的复查录像
  与被检查过的操作清单。
- 声明"完成"前，逐项确认：网格朝向、变换、挂点、动画、碰撞、镜头、操作、
  特效、UI、光照、风格。
- **凭证只放环境变量或本地密钥库**，绝不写进提交、日志、任务元数据。

---

## 四、能力不足时如实说

做不到就说做不到，并说清三件事：

1. 缺的是什么能力；
2. 试过哪些路；
3. 游戏可以接受的退路是什么（占位？换题材？缩小范围？）。

**不要**：
- 用降级方案冒充达标；
- 把"没验证"包装成"已完成"；
- 因为某条路更难就悄悄改了用户的需求。

这与本插件既有的诚实限制原则一致：宁可报告卡点，也不假装成功。
