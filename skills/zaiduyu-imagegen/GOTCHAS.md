# 生图的坑（GOTCHAS）

这份清单来自真实跑图时踩过的坑，覆盖 `pai.zaiduyu.top` 近期更新后的行为。
站点接口随时会变，遇到和本文不一致的情况，以脚本报错和 `--models` 实际输出为准。

**2026-10-30 本插件更新**：模型按「本次明确选择 > 设置页已保存默认」，没有选择不采用站点默认。模型偏好与账号独立；保存默认不登录、清空偏好不退出账号。图片生成/编辑 POST 不自动重投，旧异步失败也停止；服务器分配/节点票据问题不是账号退出登录。下述旧实测不能证明当前价格、必定不扣费或允许换模型。

## 1. 异步任务接口已下线，默认必须走同步

站点把生图改成了「直接请求上游」：旧异步任务创建接口 `/api/image-jobs` 现在直接返回
**HTTP 409**，报错信息类似「图片生成已改为直接请求上游」。

- 3.1 起脚本**默认直接调用同步生图接口**，不再等异步任务。
- 显式 `--async` 失败会停止；即使返回 404/409，也可能是已收任务后的轮询错误，绝不自动另发同步任务。
- 旧文档里「默认异步 + 轮询」的说法已经过时，按同步链路理解。

对照命令：

```powershell
# 默认就是同步，直接出图
python "<skill目录>/scripts/generate.py" --model "gpt-image-2" --prompt "..." --ratio 1:1
```

## 2. 同步出图很慢，超时别低于 300 秒

- 实测单张 `1:1` 同步出图约 **60 秒**起，4K / 高价位模型更久。
- `--timeout` 默认就是 `300`，除非你很确定，否则别再往下调。
- 让 Codex 跑命令时也要把执行超时放到 300 秒以上，否则图还没回来就被判超时。
- 多张会按网站 3 并发分批（5 张 = 3+2，6 张 = 3+3），总耗时按批次累加。

## 3. 生图前先跑 `--models` 和 `--plan`

- `--models`：只读接口，列出全部生图模型、单张积分、当前余额，不消耗积分。
- `--plan`：只展示本次预检（模型 / 单张消耗 / 张数 / 预计总消耗 / 当前积分 / 预计剩余 / 调用接口），不提交生图请求。
- 先看再选，能避免拿 700 积分的高价位模型去试一张随手图。
- 两个命令都**不扣积分**，可以放心反复跑。

## 4. 未标价模型别配 `--strict-balance`

- 有些模型在 `/api/credits` 里没有 `creditsPerRequest`，`--models` 会显示「未标价」。
- 脚本不会把「未标价」当成 0 积分。
- 但**未标价模型 + `--strict-balance` 会被直接挡下**（无法判断是否够扣）。要用未标价模型，就别加 `--strict-balance`。

## 5. Chat 链路和 Images 链路行为不同

- `images` 链路：GPT 系列，`/api/openai/v1/images/generations`，同步请求上游。
- `chat` 链路：Gemini / Grok / Z-image 等，走 Chat 多模态接口，本来就同步返回。
- 两条链路的请求体和返回结构都不一样，**报错信息也不同**；遇到问题先看预检横幅里打印的「调用接口」，判断走的是哪条。
- 图片编辑按模型分流：自定义路由模型走 JSON `images`，其余 Images 走 multipart，非图片端点才走 Chat 多模态消息接口。

## 5.1 多参考图的字段名和上限（前端实测）

- 参考图上限 **16 张**（前端常量 `Y=16`），画布编辑场景只剩 14 张（`Y-2` 留给标注底图）；单张 ≤20 MiB。
- multipart 情况下字段名随张数变化：**单图 `image`，多图 `image[]`**（重复同名文件字段），传错字段名多图会被丢。
- 自定义路由（`modelImageRouting` 里 `mode=custom`）和 `gpt-image-2-2k/4k`、`gpt-image-2.5-flare/sunburst` 改用 **JSON `images:[{image_url:"data:...;base64,..."}]`**，此时不要再发 multipart。
- 带 `-4k` 后缀的 `gpt-image-2.5-flare-4k` **不在**上面那两个全等名单里，仍走 multipart；别按前缀猜。
- 编辑请求固定 `n=1`，多张由前端并发多发几次请求；每个请求带唯一 `Idempotency-Key`。想一次要 3 张就在客户端并发 3 次，不要指望 `n=3`。
- `gpt-image-*`（`gpt-image-2` 除外）多图时会带 `input_fidelity=high`，这是前端行为，跟是否保真成功没有必然关系。

### 插件入口的参考图上传前预处理

经 `/taptap-gpt` 路由到章鱼，或使用插件 Node 入口时，会在任何站点提交前完整解码参考图并建立不可变上传快照。章鱼默认最长边 3072px、单张 2 MiB、整组 16 MiB；必要时转 WebP，保留实际透明度与比例，规范 EXIF 朝向。原图不覆盖，动画/坏图、缺处理器或超预算会以 `submitted: false` 停止，不重登、不自动换模型/通道。

这些是插件的可配置本地目标，并非站点额度/HTTP 上限，也不压缩 DSH 的完整对话 JSON。结果 `referencePreparation` 可核对处理前后信息。**直接运行本目录原始 Python 脚本不经过此预处理**，仍使用其原有 20 MiB/张、64 MiB/组校验和按内容去重规则；不要宣称原始脚本已自动压缩。

## 5.2 分辨率档位是算出来的，不是独立参数

- 站点前端把 `1K/2K/4K` 档位换算成像素尺寸再传 `size`：`1:1` 基准 1024、`3:2` 基准 1008x672、`16:9` 基准 960x540，2K 翻倍、4K 翻四倍。
- 所以 `--resolution 4K --ratio 16:9` 实际发的是 `size=3840x2160`，不是传一个 `resolution` 字段。
- 上游不接受这个尺寸时会直接报错，不会静默降级；判断依据看返回错误文本。
- 模型名里的 `2k` / `4k`（如 `gpt-image-2-4k`）是**另一个模型**，和 `--resolution` 是两套东西，别混用。

## 6. 模型列表是实时的，别写死

- 模型和价格从 `/api/config` 和 `/api/credits` 动态读取，站点随时会加新模型、改价或下架。
- 文档里的模型清单**只作格式示意**，实际以 `--models` 输出为准。
- 旧文档里写的固定「gpt-image-2 + 100 积分」已经不是唯一选择，同价位或更便宜的新模型会陆续出现。

## 7. 余额和账号信息属于隐私

- 脚本只从环境变量 `ZAIDUYU_USER` / `ZAIDUYU_PASS` 读凭据，不落盘、不打印密码。
- `--models` / `--balance` 会打印**真实余额**，别把带真实余额的终端输出直接贴出去或提交到仓库。
- 分享截图、转发日志前先把余额、账号、Cookie 抹掉。

## 8. 其他常见小坑

- 缺环境变量：脚本直接退出并打印设置方法，不会静默失败。
- `503 image_capacity_limit`：表示生成服务繁忙；付费 POST 停止，不自动重投，只有只读查询可有限重试。
- 401/403 要按阶段区分：登录接口明确拒绝才检查账号；服务器分配/票据或生成节点权限错误不等于保存账号已退出。不要盲目重登、改模型或检查明文环境凭据。
- 终端中文乱码：脚本已强制 UTF-8，仍异常就 `chcp 65001`。
- 输出默认为当前工作目录下的 `codex生图`，同名文件自动追加序号，不覆盖旧图。

## 13. 签到：奖励是限时积分；补签用 `--makeup`

`--checkin` 直接打印站点返回的原始 JSON，字段含义：

```json
{
  "enabled": true,
  "checkedIn": true,
  "reward": 557,
  "date": "2026-09-21",
  "balance": 8057,
  "validityDays": 1,
  "makeupEnabled": true,
  "makeupStreakDays": 2,
  "makeupChances": 2,
  "currentStreak": 2,
  "totalMakeups": 0
}
```

三个容易看错的地方：

1. **`reward` 进的是「限时积分」，不是永久积分。** `validityDays: 1` 表示只活 1 天。
   真实到期时刻看 `--balance` 的「最近到期」，那个值是 **UTC**，要 +8 才是北京时间
   （实测 `2026-09-22T03:04:45Z` = 北京时间 `09-22 11:04`）。
   **签到分要当天用掉**，否则过期作废。别把 `balance` 当成可用总额去规划高价模型。
2. **`currentStreak` 是连续签到天数**，只统计连续，断签归 1。
3. **`makeupEnabled` / `makeupChances` 是站点的补签能力，3.2 起有对应参数 `--makeup YYYY-MM-DD`。**
   脚本会先 `GET /api/checkin?month=` 读状态，校验补签已启用、剩余机会 >0、目标日期早于今天且未签到，
   任一条不满足就直接退出，不提交、不消耗机会。不要绕过脚本手写 `/api/checkin` 请求 ——
   猜错参数可能白白消耗补签次数，那是不可逆的。

签到接口行为（`checkin()`）：先 `GET /api/checkin` 读状态，`checkedIn=true` 就直接返回；
否则 `POST /api/checkin` 一次，**不自动重试**，防重复签到。日期按 UTC+8 判定。

## 14. 积分生命周期：永久积分不等于固定地板，限时积分每日清零

实测本机账号（2026-09-21 流水对账）：

```text
（2026-09-21 观察）永久积分当时恒为 7500。2026-10-23 实测已降到 2894，说明它并非固定地板，
一律按接口 `permanentBalance` 实时读取，不要按历史数字推断。所有赠送都进「限时积分」，validityDays = 1。
Sep 20 00:35:50  签到 +556              → 8056
Sep 20 00:36:00  兑换码 +3000（1 天有效） → 11056
Sep 21 03:00:23  限时积分到期 -3556      → 7500   ← 556 + 3000 精确清零
```

**到期是服务端自动执行的，类型 `credit_expired`，无预警推送到客户端。**
时间落在 UTC 03:00 前后（**北京时间 11:00 前后**）。

含义——**能用的钱不是 `balance`，而是「今天还剩多少」**：

- 看 `--balance` 必须**分开读**「永久积分」和「限时积分」，限时那部分今天不用就归零。
- 别按 `balance` 总额规划多天的高价模型采购，那些赠分活不到明天。
- 站点充值入口在 `/api/credits` 的 `rechargeUrl` 里（实测 `https://pay.ldxp.cn/shop/...`）。

`type` 字段速查：`checkin_reward`（签到）/ `redeem_code`（兑换码，描述形如
「限时兑换码奖励：9933（1 天有效）」）/ `register_bonus`（注册赠送）/
`referral_reward`（受邀奖励）/ `model_usage`（生图扣费，描述带模型名）/
`credit_expired`（限时到期清零）。

## 15. `--history` 的输出极大，且含非生图模型

`--history` 打的是 `/api/credits` 的**全量响应**：

- `overview.transactions` —— 流水数组，条数由 `--history-limit` 控制（默认 10）。
- `overview` 还带 `consumedCredits` / `requestCount` / `rechargeUrl` / 各类余额。
- **`pricing.models` —— 站点定价全表，不受 `--history-limit` 影响。**

那份定价表**包含非生图模型**（deepseek-v4-flash/pro、gpt-5.5、gpt-5.6-luna/sol/terra、
gpt-6-astra、mimo-v2.5、minimax-m3、ox-alpha，15~40 积分/次；其中 gpt-6-astra 是按 token 计费），
所以它和 `--models` 的清单**对不上是正常的，不是 bug** —— `--models` 只筛出生图模型。

**别把 `--history` 原始输出直接贴进对话或转给别人**：实测一次 2.6 万字符级，会刷屏，
而且里面全是真实余额。要给外部看先裁剪。

## 16. 比例保真，但像素别照文档表对

实测 `gpt-image-2` + `--ratio 3:4` 落盘 **1086x1448**，比例精确 `0.7500`。
**不是** SKILL.md 那张比例表里写的 `960x1280`。

结论：上游会按自己支持的档位**缩放尺寸**，但**宽高比保真**。

- 判「比例对不对」→ 看宽高比。
- 判「像素多少」→ 以实际落盘为准，别拿文档表去对账。
- 品牌 / 产品类题材（含商业品牌名、自有 logo 文字）**不会被上游安全策略拦**。
  被拦的是知名动漫 / 影视 / 游戏**角色**（见第 10 节）。

## 9. 比例（`--ratio` / `--size`）只在 Images 链路生效

Chat 链路的站点接口**不接受 `size` 参数**，脚本只能把它拼成一句文字提示扔进 prompt，
模型通常直接忽略。实测（2026-09-21）：

| 模型 | 链路 | 请求 | 实际输出 |
|---|---|---|---|
| `gpt-image-2` | images | `--size 1536x864` | 上游 IP 策略拦截，未出图 |
| `grok-imagine-image-2.0` | chat | `--ratio 16:9` | `768x1152`（竖版） |
| `grok-imagine-image-2.0` | chat | `--size 1536x864` + 强提示 | `768x1152`（**完全无视**） |

结论：**grok 的 chat 链路写死 `768x1152` 竖版输出，比例无法控制。**
Chat 类模型（grok / Z-image / gemini-flash-image）大概率都是这个行为。

想要**确定的比例**，只有 `--models` 里标 `images` 的模型，`--size` 才会真正下发上游。
但 images 链路目前全是 `gpt-image-*`（OpenAI 系）→ 见下一条。

## 10. 上游 IP 策略：Images 链路卡，Chat 链路放

`gpt-image-2` / `gpt-image-2-*` 对知名动漫、影视、游戏角色会返回：

```text
图片生成失败（HTTP 400）：The request was rejected by the upstream safety policy.
```

上游安全策略拒绝时说明原因并停止；不保证零扣费，不自动换模型或重复提交，不使用更宽松链路绕过安全限制。IP、商标、肖像和第三方权利必须另外核实，不能以另一个模型曾经能出图作为授权证明。

如果用户所选模型不满足合法需求、比例或计费能力，应说明限制并让用户决定；现价和可用性以站点为准，未标价不视为免费。

**现状组合拳打不通**：能过 IP 的都不能控比例，能控比例的都被 IP 拦或未开通。

### 可行出路（按优先级）

1. 接受竖版：Chat 链路直接出，比例事后再裁 —— 但 2:3 裁 16:9 会切掉头，慎用。
2. 等站点给 `gemini-3-pro-image` 配好计费，再走 images 链路拿真 16:9。
3. 用**不点名 IP 的通用描述**（"圆润的蓝色机器猫 / 戴圆眼镜的黄衣男孩"）走 images 链路试探。
   属于绕上游版权过滤，**必须先跟用户确认再执行**，不要自作主张。
4. 换站点 / 换工具。

## 11. 扩展名与内容可能不符（已修）

站点常返回 JPEG 原始字节，早期版本 `save_images()` 一律写 `.png` 后缀，导致
`.png` 文件里装的是 JPEG。3.1 本机版已加魔数嗅探（`sniff_suffix()`），自动落正确后缀。
**量尺寸要按真实格式解析**，否则拿不到真实宽高。

## 12. 换账号：改完注册表**必须重启宿主**，否则一切照旧

Windows 的用户级环境变量（`HKCU\Environment`）只对**之后新建的进程**生效，
对已运行进程**不回溯更新**。而宿主（WorkBuddy / Codex 本体）在启动时抓了一份环境快照，
它派生的所有子进程（包括跑 `generate.py` 的 shell）继承的都是**那份旧快照**，
且进程层变量会**遮蔽**注册表里的新值。

实测（2026-09-21，换号后立即在未重启的 WorkBuddy 里验证）：

```text
ZAIDUYU_USER   继承Process=6AACBAEB  注册表User=7C69BE0B  >>> 进程层遮蔽注册表，仍走旧号
ZAIDUYU_PASS   继承Process=15EF9ECA  注册表User=F3AC94F1  >>> 进程层遮蔽注册表，仍走旧号

$ generate.py --models     # 注册表已换成新号
  当前总积分：1536708       # ← 仍是旧账号的余额，新号实际只有 7500
```

所以换号是**两步**，缺一不可：

1. 写 `User` 级环境变量（注册表）
2. **重启宿主**（WorkBuddy / Codex），让它重新抓环境块

想验证有没有生效，只在**重启后**跑 `--models` 才有意义。重启前跑，看到的永远是旧号余额，
很容易误判成「没写进去」。

推论（可复用）：**任何针对本机宿主技能的「配好环境变量后立即生效」都做不到，一律需要重启宿主。**
临时绕过办法（仅单次验证用）：在同一条命令里先 `$env:ZAIDUYU_USER=...` / `$env:ZAIDUYU_PASS=...`
覆盖进程层，再调脚本 —— 这只影响那一个子进程，不改变宿主快照。

### 换号时注意

- 旧凭据被覆盖后**无法从本机恢复**，切回去要靠用户自己留的备份。
- 当前设计是**单账号全局**：只有一对环境变量，同一时间只能挂一个号。多号切换每次都要
  改注册表 + 重启宿主。要根治需改成文件凭据（`--account`，见 README 待办）。
- 新号余额可能远低于旧号（实测 1,536,708 → 7,500）。换号后先跑 `--balance` 报到，
  别默认额度还在。
